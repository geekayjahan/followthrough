# Followthrough connected v0

All ten Core features have connected source implementation. Local checks use injected test providers and synthetic fixtures; connected acceptance in `evals.md` remains **external_verification: pending**. No build or test command sends messages, writes Books records, provisions accounts or deploys this app.

## Run locally

1. Use Node.js 22.5 or newer (24 preferred). Install with `npm --prefix app install`. The only runtime package is pinned `ffmpeg-static@5.3.0`; HTTP, fetch and SQLite use Node builtins.
2. Configure `app/.env` from `.env.example`, keeping secrets there only. Set `OWNER_PASSWORD` and `APP_URL`; the default URL is `http://127.0.0.1:4310`. **Restart the server after any .env change.** A hosted runtime can supply the same keys as process environment variables; those override the file. `npm --prefix app run doctor` lists missing key names without printing values.
3. Review or replace `data/synthetic.json`. The included organisations are illustrative, not owner-provided or real. Every person email must be `@example.test`; WhatsApp identities must be configured test numbers. Map `orgs[].books_contact_id` and `lots[].books_item_id` to the fresh synthetic Books organisation. `preferred_channel:"whatsapp"` selects WhatsApp where both identities exist; otherwise intake channel determines follow-ups, with email the default.
4. Set `SYNTHETIC_DATA_APPROVED=true` only after that review and mapping. Keep `APP_LIVE=false`. Before live use, the owner must separately verify the lawful basis and authorise live sends; this build establishes neither.
5. Run `npm --prefix app start` and open `APP_URL`. The page protects every private route with owner login. It shows fresh Books numbers or an explicit unavailable state, exact pending action contents and effective test delivery recipients, stock, due-today loops and every synthetic network node/edge.
6. Keep `ENABLE_JOBS=false` and `ENABLE_POLLING=false` until intentionally enabling them. The scheduler runs only at 08:00 and 18:00 Europe/London, within two minutes, while the process is running. It never catches up later. Initial local operation does not provide a public webhook or always-on hosting.

## Provider setup

- **Zoho:** fresh Mail and Books accounts, matching OAuth region, account/organisation IDs and refresh credentials. Configure the inbox, cash account, expense account and stall customer. The client reads paginated contacts/invoices/payments/expenses and cash; it writes only approved expenses and sales receipts. Writes retain `FT-<action id>` as a reference and require resource readback. No bank or money-movement write exists.
- **Mail replies:** before live mode, outbound email goes to `OWNER_TEST_EMAILS`. Preserve the `[FT:<loop id>]` subject marker when replying from an owner test mailbox so the response binds to the synthetic loop. Unknown sender records are discarded before local persistence. Ambiguous replies hold affected drafts without closing unrelated loops.
- **WhatsApp:** set the version, phone-number ID, token, HMAC secret, verification token, up to five E.164 test numbers and owner numbers within that list. GET and POST `/webhooks/whatsapp` support verification and signed inbound messages. Unknown/non-test senders are rejected before their content is stored. Public HTTPS routing needs separately chosen hosting.
- **Closed messaging windows:** configure `WHATSAPP_WABA_ID`, `WHATSAPP_TEMPLATE_LANGUAGE`, `WHATSAPP_FOLLOWUP_TEMPLATE` and `WHATSAPP_BRIEF_TEMPLATE`. Each supported template has an approved BODY containing exactly one `{{1}}` variable, optional static FOOTER and no other components. The API verifies status, language and exact registered content. Customer drafts show the full rendered template; edits must preserve its fixed wrapper, and sending revalidates the template signature. A changed template requires a new review. No text is silently truncated.
- **Owner briefs outside the 24-hour window:** the verified brief template contains the complete draft list and dashboard URL. Approvals in this mode use the dashboard; a bare reply to a multi-action brief cannot authorise an action. Within the window, individual action controls and quoted `yes`/`yes send it` replies bind to one immutable payload. Long action text uses dashboard review. A brief that exceeds supported size is visibly blocked before sending; it is not partially labelled delivered.
- **Meta text/vision:** supply the actual owner-selected Meta open-weights model endpoint and model name. The compatible `/chat/completions` endpoint must support JSON output and image input for receipt photos. Provider failure never becomes a fabricated draft, receipt, fact or balance. Verify hosting retention/access independently.
- **Meta voice:** configure `VOICE_TRANSCRIBE_KEY`. The bundled ffmpeg normalises audio to mono WAV; complete notes longer than two minutes are rejected, not silently truncated. The API uses `muse-voice-transcribe-1.0` with `PUSH_TO_TALK`.
- **Lead enrichment:** allowlist exact public shop hosts in `ENRICHMENT_ALLOWED_HOSTS`. Retrieval pins validated public DNS and revalidates redirects; it does not run scripts. Facts require exact supporting quotes and source URLs. Below-£8 leads close even if Indian-coffee status is unknown. Missing affirmative/negative Indian-coffee evidence keeps other leads incomplete. A supplied Instagram profile requires official Business Discovery credentials and permissions; null profiles are skipped. Retrieved sources are cached once per dataset.

## Owner workflow and recovery

Pending actions do nothing until approval. Edits change their version/hash, and old controls or replies cannot authorise the revised payload. Drop closes the associated loop. Only owner identities can approve through WhatsApp. A voice refusal, ambiguous yes, stale event or replay cannot send.

Receipt photos or forwarded receipt text produce a supplier/amount/date review. Missing or unmapped facts produce a question. A cash-up needs count, grams per bag, mapped lot and GBP amount; a missing size produces a question and no Books write. Approving six 250g bags moves exactly 1.5kg after a confirmed sale. In-flight and uncertain sales reserve stock so other approvals cannot oversell it.

`needs_reconciliation` means a provider operation started without a fully confirmed local outcome. **Do not retry or recreate that write.** Review the action ID, exact payload, `FT-<action id>` reference, Books/Mail/WhatsApp receipt and provider records. The dashboard retains the uncertain action without a resend button. A verified repair must link the existing provider receipt and, for a sale, apply its stock move exactly once. This v0 deliberately has no automated uncertain-write retry or general reconciliation mutation UI.

Failed inbound processing and brief slots remain visible with event IDs and no automatic replay. Inspect `logs/actions.jsonl` and the corresponding SQLite records, resolve the configuration/model issue, and determine whether an external action started before any recovery. A failure confined to reading/classifying can be explicitly repaired and reprocessed by an operator; an uncertain write must be reconciled first. Ambiguous replies need an explicit loop marker or quoted context before the hold clears. There is no invented auto-parking or reopening policy.

The runtime pins the synthetic dataset fingerprint. After changing mappings, stop the process and preserve the entire runtime database (including any active SQLite WAL/SHM files) and action log. A fresh reviewed dataset requires an explicitly authorised new runtime store; do not silently reuse stale mappings or discard unresolved action evidence. `.env`, SQLite files, runtime logs and browser QA output are gitignored.

## Local verification

- `npm --prefix app test`: committed deterministic domain, request-contract, HTTP, auth/HMAC, source, concurrency and restart checks. Provider responses in these tests are injected test-only evidence.
- `npm --prefix app run check`: syntax-checks source, browser JavaScript and checks.
- `node app/checks/secret-scan.mjs`: scans publishable source for high-confidence token and private-key patterns without reading ignored credentials or printing matched values; this is not a comprehensive security audit.
- `node app/checks/serve-ui-fixture.mjs`: isolated browser QA at `http://127.0.0.1:4311`, password `test-owner-only`. It does not read `.env`, uses a temporary SQLite store and injected providers, and displays a TEST FIXTURE ONLY banner. Production has no mock/demo environment switch.
- With a fresh fixture running, from the `app` directory run `npx --yes --package @playwright/cli playwright-cli -s=followthrough-v0 open http://127.0.0.1:4311`, then the same CLI with `-s=followthrough-v0 run-code --filename=checks/browser-smoke.mjs`. These nine browser checks use only the isolated fixture and save ignored desktop/phone screenshots.

Verified on 29 October 2026 against runtime source `9eba725`: 33 automated checks passed, syntax checks passed, and the source secret-pattern scan found zero matches. Independent S2 artifact review passed 7/7. All nine browser cases in `checks/browser-smoke.mjs` passed at desktop and phone sizes, including edited-draft approval, one test receipt, shipment closure across reload, network selection, London dates, and zero final console errors. All browser provider responses were isolated fixtures.

The acceptance map remains in `feature-list.json`; canonical behaviour is `spec.html`. External proof still requires configured fresh accounts, actual inbox delivery, actual Books write/readback, real model and voice responses, webhook hosting and a 24-hour brief observation. Local passing checks do not satisfy those connected evals.
